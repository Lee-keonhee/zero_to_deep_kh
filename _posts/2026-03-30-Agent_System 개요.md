# Agent 시스템

### 1. Agent는 왜 필요할까?
#### 1-1 LLM의 구조적 한계

LLM(Large Language Model)은 방대한 텍스트 데이터를 학습해 언어 이해와 생성에 탁월한 성능을 보이지만, 본질적으로 **"입력 → 출력"의 단발성 추론 엔진**에 불과함. 이로 인해 다음과 같은 구조적 한계가 존재함.

- **수동성** : 사용자의 질문에 반응할 뿐, 스스로 목표를 설정하거나 행동을 개시하지 못함.
- **무상태성(Stateless)** : 각 요청은 독립적으로 처리되어, 이전 맥락을 스스로 유지하지 못함.
- **실행 불가** : 텍스트 생성에 그칠 뿐, 코드 실행·파일 처리·API 호출 등 실제 작업을 직접 수행할 수 없음.
- **정보 단절** : 학습 데이터의 시점(cutoff)에 묶여 있어, 실시간 정보나 외부 시스템에 접근이 불가함.
#### 1-2 Agent 시스템의 등장 배경
실세계의 문제는 대부분 단일 질의응답으로 해결되지 않음. 
목표 달성을 위해 **여러 단계의 추론, 외부 정보 수집, 도구 활용, 결과 검증**이 복합적으로 요구됨.
Agent 시스템은 LLM을 단순한 텍스트 생성기가 아닌 **자율적 실행 주체**로 확장함으로써 이러한 요구를 충족함.

#### 1-3. 실제 적용 사례

| 도메인      | 사례       | Agent가 수행하는 흐름                 |
| -------- | -------- | ------------------------------ |
| 소프트웨어 개발 | 개발 자동화 봇 | 요구사항 분석 → 코드 작성 → 테스트 → 디버깅    |
| 정보 수집    | 리서치 봇    | 키워드 설정 → 웹 검색 → 정보 정제 → 보고서 작성 |
| 고객 서비스   | 고객응대 봇   | 문의 접수 → DB 조회 → 답변 생성 → 티켓 처리  |

### 2. Agent 시스템의 정의

#### 2-1 정의

Agent 시스템이란, 사용자로부터 목표를 전달받아 **스스로 계획을 수립하고, 도구를 활용하며, 그 목표를 자율적으로 완수하는 시스템**
단순히 LLM을 호출하는 것을 넘어, 추론-실행-관찰의 루프를 반복하며 복잡한 작업을 처리하는 자율적 실행 주체임.
최종 목표만 주어지면 세부 실행 계획은 스스로 판단하며, 외부 도구·API·DB 등과 연동해 실세계에 직접 작용하고, 작업이 완료될 때까지 맥락과 중간 결과를 지속적으로 유지함.

#### 2-2. 구성 요소 개요

Agent 시스템은 크게 아래 요소들의 유기적 결합으로 성립됨. 각 요소는 이후 단계에서 상세히 다룸.

| 구성 요소      | 역할                 |
| ---------- | ------------------ |
| Perception | 외부 입력을 인식하고 해석     |
| Memory     | 맥락과 정보를 저장하고 유지    |
| Planning   | 목표 달성을 위한 실행 계획 수립 |
| Tool Use   | 외부 도구 및 API 활용     |
| Execution  | 계획을 실제 행동으로 수행     |
| Reflection | 결과를 평가하고 자기 개선     |

### 3. LLM vs Agent

LLM과 Agent는 흔히 혼용되지만, 본질적으로 역할과 동작 방식이 다름. LLM이 **"지식의 창고"** 라면, Agent는 그 지식을 활용해 실제로 **"행동하는 주체"** 임.

|구분|LLM|Agent|
|---|---|---|
|역할|텍스트 생성 및 추론|목표 달성을 위한 자율적 실행|
|동작 방식|수동적 (질문에 반응)|능동적 (스스로 단계를 결정)|
|상태|Stateless (맥락 유지 불가)|Stateful (맥락과 기억 유지)|
|실행 범위|텍스트 입출력에 한정|도구 호출, API 연동 등 실세계 작용|
|작업 단위|단일 요청-응답|목표 달성까지 반복적 루프 수행|
|판단 주체|사용자가 다음 행동 결정|Agent가 다음 행동을 스스로 결정|
LLM과 Agent는 대립 관계가 아님. Agent는 LLM을 **두뇌(추론 엔진)** 로 탑재하여, 그 위에 Memory·Tool·Execution 등의 레이어를 추가한 상위 시스템임. 즉, **LLM은 Agent의 핵심 구성 요소**이며, Agent는 LLM의 능력을 실세계로 확장한 시스템임.

### 4. 핵심 개념 및 요소
#### 4-1. 개념적 특성 

Agent 시스템을 정의하는 본질적인 특성은 다음과 같음.

- **목표 지향성** : 단발성 응답이 아닌, 최종 목표 달성을 위해 다단계로 동작함.
- **자율적 판단** : 주어진 목표 안에서 세부 실행 계획은 스스로 결정함.
- **환경 상호작용** : 외부 도구·API·DB 등과 연동하여 실세계에 직접 작용함.
- **상태 유지** : 작업 진행 중 맥락과 중간 결과를 지속적으로 유지함.

#### 4-2. 기능적 요건

Agent 시스템이 성립하기 위해 반드시 갖춰야 할 조건은 다음과 같음.

- **자율성 (Autonomy)** : 인간이 일일이 지시하지 않아도, 최종 목표만 주어지면 세부 실행 단계를 스스로 판단함. 단순히 명령을 따르는 것이 아니라, 현재 상황을 해석하고 다음 행동을 스스로 결정하는 능력이 핵심임.
- **지속성 (Persistence)** : 한 번의 응답으로 끝나는 것이 아니라, 목표가 달성될 때까지 프로세스를 유지하며 환경과 상호작용함. 중간에 오류가 발생하더라도 이를 감지하고 재시도하거나 대안을 모색하며 작업을 이어나감.
- **도구 활용 (Tool Use)** : 내부 지식만으로 해결할 수 없는 작업을 위해, 검색 엔진·코드 실행기·API·데이터베이스 등 외부 도구를 적재적소에 활용함. 어떤 도구를 언제 사용할지 판단하는 것 자체도 Agent의 핵심 능력 중 하나임.
- **반응성 (Reactivity)** : 환경의 변화나 예상치 못한 오류에 유연하게 대응하는 능력. 계획이 틀어졌을 때 고집하지 않고 즉각 재판단함.

### 5. Agent의 종류

#### 5-1. 구조 기반 분류

Agent는 내부 구조와 의사결정 방식에 따라 다음과 같이 분류됨.

|유형|설명|특징|
|---|---|---|
|Simple Reflex Agent|현재 입력에만 반응해 즉각적으로 행동|상태 유지 없음, 단순 규칙 기반|
|Model-based Agent|내부 상태 모델을 유지하며 판단|과거 맥락을 고려한 의사결정 가능|
|Goal-based Agent|목표를 설정하고 달성을 위한 행동을 선택|다단계 계획 수립 가능|
|Utility-based Agent|목표 달성뿐 아니라 최적의 방법을 선택|여러 선택지 중 가장 효율적인 경로 탐색|
|Learning Agent|경험을 통해 스스로 성능을 개선|반복 수행을 통해 점진적으로 고도화|

#### 5-2. 구성 방식 기반 분류

실제 Agent 시스템 설계에서는 단일 Agent로 구성하는지, 여러 Agent를 조합하는지에 따라 크게 두 가지로 나뉨.

- **Single Agent** : 하나의 Agent가 모든 태스크를 처리함. 구조가 단순하고 관리가 용이하지만, 복잡한 작업에서는 한계가 있음.
- **Multi-Agent** : 여러 Agent가 역할을 분담하여 협력함. Orchestrator(지휘자)가 전체 흐름을 관리하고, Subagent(실행자)들이 각자의 전문 태스크를 수행하는 구조로 설계됨. 복잡하고 대규모의 작업에 적합함.

### 6. Agent 전체 구조도

#### 6-1. 전체 아키텍처 개요

Agent 시스템은 LLM을 중심으로, Perception·Memory·Planning·Tool Use·Execution·Reflection이 유기적으로 연결된 구조임. 각 구성 요소는 독립적으로 존재하는 것이 아니라, **하나의 순환 구조 안에서 서로 데이터를 주고받으며 동작**함.

#### 6-2. 구조도

```
외부 환경 (사용자 입력 / API 응답 / 파일 등)
          │
          ▼
   ┌─────────────┐
   │  Perception │  ← 외부 입력을 인식하고 해석
   └─────┬───────┘
         │
         ▼
   ┌─────────────┐        ┌──────────────┐
   │   Memory    │ ◄────► │   Planning   │  ← 맥락을 바탕으로 계획 수립
   └─────────────┘        └──────┬───────┘
                                 │
                                 ▼
                          ┌──────────────┐
                          │   Tool Use   │  ← 필요한 도구 선택 및 호출
                          └──────┬───────┘
                                 │
                                 ▼
                          ┌──────────────┐
                          │  Execution   │  ← 실제 행동 수행
                          └──────┬───────┘
                                 │
                                 ▼
                          ┌──────────────┐
                          │  Reflection  │  ← 결과 평가 및 재판단
                          └──────┬───────┘
                                 │
                         목표 달성 여부 판단
                                 ├── 미달성 → Planning으로 되돌아감
                                 └── 달성 → 종료
```

#### 6-3. 핵심 흐름 요약

외부 입력을 **Perception**이 인식하면, **Memory**에 저장된 맥락을 참조해 **Planning**이 실행 계획을 수립함. 이후 **Tool Use**를 통해 필요한 도구를 호출하고, **Execution**이 실제 행동을 수행함. 마지막으로 **Reflection**이 결과를 평가하여 목표 달성 여부를 판단하고, 미달성 시 다시 Planning 단계로 돌아가는 **순환 구조**로 동작함.

### 7. ReAct 작동 루프

#### 7-1. ReAct란?

ReAct는 **Re**asoning + **Act**ing의 합성어로, Agent가 추론과 행동을 번갈아 수행하며 목표를 달성하는 패턴임. 단순히 행동만 하거나 추론만 하는 것이 아니라, **"생각하고 → 행동하고 → 관찰하는"** 과정을 목표 달성까지 반복하는 것이 핵심임.

#### 7-2. 작동 루프

|단계|명칭|설명|
|---|---|---|
|1|**Perceive (인식)**|사용자의 요청이나 환경 변화를 감지하고 입력을 해석함|
|2|**Think (추론)**|현재 상황에서 목표에 가까워지려면 무엇을 해야 할지 판단함|
|3|**Plan (계획)**|실행할 구체적인 단계와 사용할 도구를 선택함|
|4|**Act (실행)**|코드 실행, API 호출 등 실제 행동을 수행함|
|5|**Observe (관찰)**|실행 결과를 확인하고 성공 여부를 판단한 뒤, 미달성 시 2번으로 돌아감|

#### 7-3. 6번 구조도와의 관계

ReAct 루프는 6번에서 다룬 전체 구조도의 **동작 원리**에 해당함. 구조도가 "무엇으로 이루어졌는가"를 설명한다면, ReAct 루프는 그 구조가 **"어떻게 흘러가는가"** 를 설명함.

```
Think → Plan     =  Planning
Act              =  Tool Use + Execution
Observe          =  Reflection
```
